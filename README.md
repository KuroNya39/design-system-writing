# design-system-writing

给项目建立 / 维护设计系统，或者拿一套现成的界面规则去改界面、审界面——可直接装进 AI agent 的 Skill。

三种用法：**建系统**（读仓库与真实运行画面 → 盘点问题 → 定规则 → 落地 token 与规范）、**取约束**（改界面前先拿一份「照这个做、别自己发明」）、**审界面**（照规则复查：不统一、状态残缺、动效各写各的、踩了实现陷阱）。全程只把**审美取舍**交给你拍板，其余自己查。

## 内置规则集

- **设计语法** —— 可复用的取舍准则，分三层（顺序即推理顺序）：
  **结构与体验**：信息架构 / 单列优先 / 渐进披露 / 任务流 / 三态 / 文案 / 错误预防。
  **交互**：完整状态组 / 悬停总则 / 主输入 / 命中目标 / 按下即反馈 / 输入约束 / 拖拽 / 键盘与焦点 / 可中断。
  **视觉**：间距网格 / 字号与行高 / 字重治理 / 语义色彩 / 组件几何 / 图标治理 / 造型口味 / 无障碍。
  每条给「为什么」和「落地检查」。
- **动效语法** —— 该不该动（按操作频率判定）/ 每个动效要能说出目的 / 缓动与时长档位 / 空间一致性 / 用 transition 不用 keyframes / 速度交接 / 减少动效降级。含一条实测教训：**过陡的 ease-out 就是「突兀」本身**，别把它当成「有分量」；CSS 与图表库等多套实现必须同族。
- **实现陷阱** —— 十六类「踩过才知道」的工程事实，每条给「现象 → 为什么 → 做法 → 检查」：浏览器默认样式反扑、`:hover` 在指针捕获期间失效、自绘滚动条是 CSS + JS 两半、焦点环被滚动容器裁切、样式权重战争、浮层互切要交叉过渡、遮罩关闭要判「按下与松开同源」、可中断的动效别用 keyframes、焦点在元素消失时丢掉、别在元素不可见时量尺寸、内容撑高的浮层要「数据到手才开窗」、别用「重叠 + 遮挡」伪造形状、原生控件（尤其 `<select>`）默认要接管等。

## 安装

把下面这段话发给你的 AI agent：

> 把 https://github.com/KuroNya39/design-system-writing 装成我的 skill：仓库里的 `SKILL.md` 放进你的 skills 目录，目录名用 `design-system-writing`。装好后告诉我怎么确认它生效了。

装完重开一次 agent；想升级，跟它说「把 design-system-writing 更新到最新」。

## 调用

- **直接说人话**：「用 design-system-writing 给这个项目建一套设计系统」——带上 skill 名最稳，不带也多半能认出来
- **斜杠命令**（支持的 agent）：`/design-system-writing`
- 只想改界面或复查：说「按 design-system-writing 审一遍这个界面」即可

## 适用场景

- 项目还没有设计系统，配色 / 间距 / 字号靠手感——建一份 `design-system.md` + 设计 token 当单一依据
- 已有规范，改了 UI / 新增 token 后回来同步
- 改界面前先拿一份约束，避免风格漂移
- 界面被指出不统一：同样控件两个样、颜色乱、图标混用、可点卡片悬停各写各的、原生下拉没接管、图标位置看着怪
- 界面「看着规范、用起来别扭」：点了没反应、空态没做、按钮全叫「确定」、键盘走不通、动效各写各的时长

## 工作方式

按 A–G 七个阶段推进，全程半自动：

| 阶段 | 做什么 |
|---|---|
| **A · 项目侦察** | 识别技术栈与样式方案、盘点界面与语义，不统一点列成带 `file:line` 的档案 |
| **B · 先确认需求，再问取舍** | **B0** 先跟人确认交付物 / 范围 / 什么算做完（不可跳过，没确认不改代码）；**B1** 才问审美取舍（气质 / 主色 / 图标库 / 尺寸档位 / 动效胃口），每题带推荐答案，可「全按推荐」 |
| **C · 设计语法** | 用内置准则定规则：结构与体验 → 交互 → 视觉；动效单独一节 |
| **D · 实现陷阱** | 十六条工程坑清单，落地前先避开 |
| **E · 样张先行 → 落地实现** | **先做一屏给人看、拿到反馈再铺开**（方向错了一屏返工，不是全站返工）；再按技术栈写设计 token（primitive → semantic）、组件规格表、规范文档 |
| **F · 校验审计** | **按「界面实例清单」审计**——每个按钮 / 可点容器 / 图标控件 / 原生控件 / 图表 / 浮层各一行，不允许「既没归类也没例外」；静态扫裸值 / 非档位值 / 状态残缺；规范 ↔ token ↔ 代码三方一致；动效要**跑起来量**（CSS 与图表库两边对账）；只用键盘走一次主任务 |
| **G · 交付维护** | 交付审计报告；新增 / 改 token 走五步流程（第一步先查旧 token 有没有人用） |

## 产出物

- **规范文档** —— 设计原则、语义色与映射、度量档位表、状态模型与悬停总则、体验与任务流、交互规格、动效规格、图标策略、组件速查表、无障碍清单、改动自检清单
- **设计 token** —— Primitive → Semantic（→ Component）三层，按技术栈落地成 CSS 变量 / Tailwind theme / Design Tokens JSON；含拼好的 transition 与交互常量
- **组件规格表** —— 状态组 × 属性，含命中区、键盘操作、进出场动效，值一律引用 token
- **审计报告** —— 通过项与不合规点，附修法

## 它不做

- **不产同款皮肤** —— 规则集是通用取舍准则，不是某产品的成品目录；产出按你的技术栈与偏好落地
- **不产组件库代码** —— 它定规则、给规格，不写组件实现；落地仍是开发者的事
- **不替你审美** —— 气质、主色、图标库、圆角密度这类取舍会问你，每题带推荐答案
- **不跳过需求确认** —— 动手前先确认交付物 / 范围 / 完成判据（B0），没确认不动代码
- **不静默改对外文档** —— 规范文档与 README 的改动，会先给你看「改哪句、改成什么样」
