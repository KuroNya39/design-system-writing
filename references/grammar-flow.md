# 设计语法 · 结构与体验（G1、G2、G13、G14）

规则集分四册，G 编号跨文件连续：本册管流程、反馈与文案；交互与动效见 `grammar-interaction.md`，视觉见 `grammar-visual.md`，图表、表格与无障碍见 `grammar-data.md`。默认档位在 `defaults.md`，本册只留治理规则。

## G1 布局与信息架构（IA）
| 语法 | 为什么 | 落地检查 |
|---|---|---|
| **单列优先**：内容默认一列到底，横向确有空间且并排确有语义时才多列。 | 窄窗不重排；多列是为「对比 / 配对」服务，不为塞满。 | 最窄档是一列；没有「为了好看硬并排」的列。 |
| **内容列有宽度上限并居中**：正文列设 `max-width` + 自动外边距。 | 行长失控读起来累。 | 宽窗下拉一下，内容列不离散；窄窗不截断。 |
| **断点取内容开始拥挤的位置**，不抄设备宽度；档位只留真正需要的少数几档。 | 断点是内容问题，不是机型问题。 | 断点表能说出每一档对应哪个组件开始挤。 |
| **渐进披露**：核心内容先出现，次要 / 高级内容收进折叠、二级页或浮层。 | 首屏只留一条主路径。 | 首屏 = 主任务可达；进阶项都在折叠 / 二级。 |
| **邻近成组**：相关内容放一起，分组靠间距，不靠描边线框。 | 间距即分组语言。 | 组内小档、组间中档、页间大档。 |
| **留白即层级**：重要的东西周围要空；拥挤 = 什么都不重要。 | 焦点由留白让出。 | 主 CTA 上下留白 > 次要元素。 |
| **尺寸主导层级**：越大越重要，辅以字重与灰阶；颜色不作唯一信号。 | 层级先从字号 / 面积读出。 | 同级标题同档同色；一屏能排出主次。 |
| **层级公式**：模块标题、字段标签、主 CTA 各定一套「字号 / 字重 / 颜色」，同级不许一大一小。 | 逐处临时决定必然漂移。 | 一屏内字号 2–3 档；同级标题完全同款。 |

## G2 体验与任务流（UX）
| 语法 | 为什么 | 落地检查 |
|---|---|---|
| **沿用既有约定**：导航在哪、关闭在哪、垃圾桶 = 删除。 | 心智模型来自用户用过的所有软件。 | 每个交互都能说出「在哪见过同样的做法」。 |
| **一屏一个主任务**：每屏能指出唯一主行动，其余退为次要或下沉。 | 两个并列主行动等于没有。 | 一屏只有一个实心主按钮（见 G7）。 |
| **主路径最短**：常见任务一步到位，高级项下沉。 | 每多一个必经的次要选择都是日常摩擦。 | 主任务能数出步数，没有一步是为「顺便配置」。 |
| **一次只要求一个决定**：选项多到一屏扫不完就分组或给搜索。 | 选择本身就是成本。 | 长列表有分组 / 搜索 / 合理默认值。 |
| **错误预防优于错误提示**：能禁则禁、能默认就默认、能约束就约束。 | 事后报错更贵。 | 每个提示过的错误，都先问过「能不能从源头不让它发生」。 |
| **破坏性动作给撤销，而非一律弹确认**：只有不可逆且代价高的才拦一次。 | 确认弹窗用滥了会被无脑点过。 | 破坏性动作要么可撤销，要么有确认——不要两者都做足的假安全。 |
| **三态齐全**：每个数据界面都要设计 空态 / 加载态 / 错误态。 | 只设计「有数据」的样子，另三种一定像没做完。 | 三态都能指出来；空态给下一步动作，不是干放一句「暂无数据」。 |
| **操作后立刻有可见反应**，完成后再给终态（通道选择见 G13）。 | 无反馈会让用户重复点击。 | 异步动作在 100ms 内进入加载态。 |
| **文案即界面**：按钮写动词 + 结果；错误说清「发生了什么 + 怎么办」。**界面能说清的事不要推给文档**——不写「详见 README」。 | 界面上的字是用户唯一能读的。 | 按钮脱离上下文也读得懂；错误提示不含「出错了」这类零信息句。 |
| **一致性**：同样的事在不同地方同名、同形、同位。 | 每个不一致都要重新学一次。 | 同一个概念全站只有一个叫法。 |

## G13 反馈与确认

**每个操作都要有可见结果，且走对的通道。** 选错通道比不做更糟：成功弹确认框会训练用户无脑点掉，失败只改一行小字等于没发生。

| 场景 | 通道 |
|---|---|
| 不可逆且代价高的动作（删除、清空、覆盖、中断进行中的任务） | 确认弹窗 |
| 阻塞主流程、必须处理的失败 | 对话框（说清原因 + 下一步） |
| 成功 / 已生效 | Toast，或就地改变状态 |
| 失败但流程能继续 | 错误 Toast（带原因，不只写「失败」） |
| 没有数据 | 空态（一句说明 + 下一步动作，见 G2） |
| 长任务 / 部分成功 | 结果摘要（成功多少、失败多少，失败可重试） |

- **失败不许静默**：每一处错误都要落到可见反馈上。只打控制台日志，在用户眼里就是「点了没反应」。
- **加载挂在触发它的控件上**：原地转圈 + 真正禁用、文字不变（见 G4）。不要用「正在…」Toast 顶替加载态——它不在视线落点上，慢任务里还会堆成一串。
- **确认不能被绕过**：不可逆动作要么可撤销，要么有确认，至少其一（见 G2）；不要用「默认选中危险项」把确认做成摆设。
- **确认框要压过所有普通弹窗**：给它单独的层级 token（见 `defaults.md` 的层级带），**不要写成「普通弹窗层级 + N」**——普通弹窗自己也可能加偏移，加着加着就顶到确认框上面。
- **关闭的是「这一层」，不是整个流程**：叠在另一层上的弹窗（编辑器、详情页），Esc / 点空白应返回下一层，而不是把两层一起关掉、掉回主界面——除非它确实是独立弹窗。

## G14 文案与用词

**界面上的字是产品的一部分，不是装饰。** 同一个动作全流程同一个词，同一个概念全站同一个名字。

| 位置 | 写法 |
|---|---|
| 弹窗标题 | 以动作动词提问（「删除这批记录？」「退出软件？」），不写「提示」「警告」这类空标题 |
| 弹窗正文 | 说清后果（会丢什么、影响谁），不重复标题 |
| 普通按钮 | 取消 / 确定；两个字的短词放得下就用短词 |
| 危险按钮 | 用动作本身的词（删除 / 清空 / 退出），不写「确定」；配对按钮仍写「取消」 |
| 导航类按钮 | 写去向或结果（「查看详情」「返回列表」），不写「确定」 |
| 错误提示 | 发生了什么 + 怎么办；不写「出错了」「操作失败」这类零信息句 |
| 空态 | 一句说明 + 一个下一步动作 |
| 状态词 | 同一语境只留一套词表，不混近义词（同一处不要既写「进行中」又写「处理中」） |
| 动态值 | 用「」包起来，与周边固定文字拉开 |

- **句子带标点，标签短语不带**：完整句子以句号收尾；按钮、标签、状态词、表头、Toast 短语不写句号。
- **中文与字母 / 数字之间留空格**（「共 12 人」「3 个批次」）。
- **一个动作一个词**：按钮、Toast、确认框、错误提示里用同一个动词——按钮叫「清空」，提示就不叫「删除」。
- **提示里点名界面元素时，用与界面上完全一致的字**：按钮写「重试」，提示里也写「重试」。
